## Description

From the 2026-09-25 architecture review, roadmap item A3 (`design/refactors/ARCHITECTURE_ROADMAP.md` §A, direction 3). Groomed in task 056 pass 1; re-verified 2026-10-01 at `404b51c`. Line numbers are from that commit.

The side of a trigger event lives in the event's name, not on the context. Handlers that should work for both sides need two registrations, branch on `ctx.event_type` to find the side, and the pairs have gaps. Trap and rune data use two opposite conventions for the same field type.

### The enum

`Enums.TriggerEvent` (Enums.gd:58-114) has 32 values; 24 are `ON_PLAYER_*` / `ON_ENEMY_*`. Only 9 are exact pairs: TURN_START, TURN_END, MINION_PLAYED, MINION_SUMMONED, MINION_DIED, MINION_SACRIFICED, SPELL_CAST, TRAP_PLACED, SPARK_CONSUMED. The rest:
- Attacks: `ON_PLAYER_ATTACK_PRE` and `ON_PLAYER_ATTACK_POST` (:73-74) vs one `ON_ENEMY_ATTACK` (:90, "fires BEFORE attack").
- Hero damage: the unprefixed `ON_HERO_DAMAGED` (:93) is the player's; `ON_ENEMY_HERO_DAMAGED` (:94) is the enemy's.
- `ON_PLAYER_CARD_DRAWN` (:68) has no enemy twin. `ON_PLAYER_ENVIRONMENT_PLACED` (:75) is never fired (deleted by task 088).
- Side-less values carry the side in `ctx.owner` already: ON_RUNE_PLACED, ON_RITUAL_ENVIRONMENT_PLAYED, ON_RITUAL_FIRED, ON_CORRUPTION_REMOVED, ON_FORMATION_TRIGGERED.

References to the side-specific values outside Enums.gd: 247 (CombatSetup 108, CombatState 40, TriggerHandlerTests 39, CardDatabase 14, CommandTests 12, CombatHandlers 10, DamageTypeTests 9, CardEffectTests 4, CombatManager 4, LiveSmokeTests 3, TriggerManager 3 in its doc comment, TrapCardData 1). All 31 production `EventContext.make` sites pass an owner equal to the event's prefix side (e.g. CombatState.gd:2451-2452 picks `ON_PLAYER_TURN_START if side == "player" else ON_ENEMY_TURN_START` and passes `side`). That is what lets a shim key on (kind, side) without changing dispatch.

### Registrations and handlers

- `debug/tests/snapshots/handler_order.txt` pins 123 registrations on 24 events (generated by `_handler_order_snapshot`, TriggerHandlerTests.gd:3474-3504, from `TriggerManager.dump_order`, TriggerManager.gd:91-102, which sorts by event id and prints `Enums.TriggerEvent.find_key`).
- 11 handlers (counting `_on_trap_route`) are registered on both the player and the enemy variant of one event, e.g. `on_minion_event_presence_auras` six times (CombatSetup.gd:570-575).
- The registry has 79 trigger entries, all on absolute events. 66 of the 102 `func on_` handlers in CombatHandlers carry a side in their name.
- Handlers recover the side from the event type: CombatHandlers.gd:36/:71/:77 (`_run_env_passives_for_turn(event_type)`), :52, :1012-1016, :1112, :1405-1407, :2336, and CombatState.gd:1024 in `_on_trap_route`.
- The snapshot doesn't see dynamic registrations: rune auras (CombatState.gd:781-811), environment rituals (:373-379) and grand-ritual lambdas (CombatSetup.gd:625-632).

### Gaps the pairs leave (all latent with today's enemy content)

1. **Enemy attacks have no PRE/POST and no defender.** CombatManager fires PRE and POST only `if attacker.owner == "player"` (CombatManager.gd:85, :110 for minion targets; :163, :177 for hero targets). The enemy gets one `ON_ENEMY_ATTACK` before resolution from `_fire_enemy_attack_declared` (CombatState.gd:3086-3097), which sets only `ctx.minion` and returns early for the player (`if side != "enemy" …`). The player's attack has no declaration step, so nothing can cancel it.
2. **Attack riders run at different times per side.** `on_attack_fire_riders` is registered on `ON_PLAYER_ATTACK_POST` and on `ON_ENEMY_ATTACK` (CombatSetup.gd:603-604). It needs `ctx.defender` to be a minion or a hero string (CombatHandlers.gd:467-470), so on the enemy's pre-damage event it does nothing. The comment at :443-445 says the enemy side "matches every other attack-driven effect". `Enums.mirror_trigger` maps both PRE and POST to `ON_ENEMY_ATTACK` (Enums.gd:137-139), so a rune with an attack trigger would lose the distinction.
3. **Enemy-owned standard traps can never spring.** Rune aura triggers are written from the owner's view and mirrored for enemy owners (CombatState.gd:787, :799, :804). Non-rune trap triggers are matched exactly: `if not trap.is_rune and trap.trigger == trigger` (:1041). All four trap cards use player-view triggers: `hidden_ambush` and `smoke_veil` `ON_ENEMY_ATTACK` (CardDatabase.gd:2117, :2128), `silence_trap` `ON_ENEMY_SPELL_CAST` (:2139), `death_trap` `ON_ENEMY_MINION_SUMMONED` (:2150). TRAP_ROUTES (:1010-1020) springs enemy-owned traps only on `ON_PLAYER_MINION_SUMMONED`, `ON_PLAYER_SPELL_CAST` and `ON_PLAYER_TURN_START`, so even those three routes can't spring an existing card, and there are no enemy routes for the player's attack, a friendly death or hero damage. The probe `_trap_route_enemy_trap_on_player_turn_start` (TriggerHandlerTests.gd:3451-3467) pins today's absolute semantics.
4. **Enemy draws fire no trigger.** `_fire_card_drawn` (CombatState.gd:1597-1602) is called only for the player (:1570, :1593-1594).

Enemy content reaching these paths today: none. In `encounter_decks.json` (23 decks; user data dir until task 047 lands) the enemy's traps are runes only (Dominion and Blood in f2_c and f5_a, Shadow in f4_b), no deck has `banner_of_the_order` (the only GRANT_ATTACK_RIDER source, CardDatabase.gd:843) and none has a non-rune trap. The enemy-side champion listeners on `ON_ENEMY_ATTACK` (`on_enemy_attack_champion_rip`, `_rs`; CombatSetup.gd:287, :363) don't read `ctx.defender`.

### Consequence

Every new mechanic that should work for both sides needs paired registrations and a fresh decision about which absolute event an enemy-owned copy hears; a missing pair fails silently. An enemy hero, a mirror match or PvP would need a re-audit of all 247 references.

## Decision (owner, 2026-10-01)

- Q2: no mechanic is one-sided by design; who has what is data and config.

## Proposed fix

Phased. Phases 1–3 are the narrow, behaviour-neutral migration; phases 4–5 change behaviour (latent today). Scope boundaries:
- Firing ON_RUNE_PLACED / rituals for the enemy, and per-side ritual storage: task 093.
- `on_minion_turn_start_passives` and the legacy `passive_effect_id` dispatchers: task 089.
- Per-side talents and hero passives (`SideState` storage, enemy talents from config, `_card_ctx`): task 090.
- The `enemy_play_target` / `attack_cancelled` side channels: task 129 (roadmap I1). Phase 2b leaves the two on-play handlers (CombatHandlers.gd:951-970, prio 10, reads `ctx.target`; :976-996, prio 5, reads `state.enemy_play_target`) as two registrations until 129 removes the side channel.

## Phases

Each phase is its own commit with its own gate run. Open a sub-task per phase when starting, as LIVE_SIM_UNIFICATION_PLAN did.

### Phase 1: TriggerKind and the shim (A-core P1; byte-identical)

- `Enums.TriggerKind`: TURN_START, TURN_END, CARD_DRAWN, MINION_PLAYED, MINION_SUMMONED, MINION_DIED, MINION_SACRIFICED, SPELL_CAST, TRAP_PLACED, ATTACK_DECLARED (today's `ON_ENEMY_ATTACK`: before resolution, cancellable), ATTACK_PRE, ATTACK_POST, HERO_DAMAGED, SPARK_CONSUMED, RUNE_PLACED, RITUAL_ENVIRONMENT_PLAYED, RITUAL_FIRED, CORRUPTION_REMOVED, FORMATION_TRIGGERED.
- Tables legacy → (kind, side) and back; side-less legacy values map to (kind, any).
- `EventContext.kind` and `EventContext.make_kind(kind, side)`. `make_kind` also fills `event_type` with the legacy value (or -1 where none exists), so existing `ctx.event_type ==` branches keep working.
- TriggerManager stores entries per kind, each with a side filter (`CombatSide.PLAYER` / `ENEMY` / any). A legacy `register(event, …)` becomes `register_kind(kind_of(event), side_of(event), …)`. `fire` derives (kind, side) and skips entries whose filter doesn't match. Entries stay ordered by (priority, registration order); filtering a stable list by side keeps each side's relative order, so dispatch is unchanged. `unregister` accepts both forms (`unapply_passive`, rune and environment removal).
- `dump_order` keeps printing legacy event names, grouped and sorted as today, so handler_order.txt is unchanged.
- `TestHarness.fire` gains a kind overload.
- Add the dynamic-order probe (Verification) now, so it guards phases 2–3.

### Phase 2: migrate one event family per commit (A-core P2a–P2d, A-paths A3c; byte-identical)

Fire sites move to `make_kind(kind, side)`; registrations move 1:1 to (kind, side) (don't merge a player/enemy pair into one registration yet; that changes the snapshot); handler branches on `ctx.event_type` move to `ctx.owner`.
- **2a turn:** TURN_START / TURN_END. Fire sites CombatState.gd:2450-2452, :2459-2461. Branches CombatHandlers.gd:36, :52, :71, :77, :1405-1407, :2336.
- **2b minion lifecycle:** MINION_PLAYED / SUMMONED / DIED / SACRIFICED. Branches CombatHandlers.gd:1012-1016, :1112; the trap route's friendly-death check, CombatState.gd:1024.
- **2c cards and resources:** CARD_DRAWN, SPELL_CAST, TRAP_PLACED, SPARK_CONSUMED. Fire CARD_DRAWN for both sides in `draw_cards` and `add_to_hand`; the only listener (`on_card_drawn_void_echo`, a talent) is registered for the player, so nothing changes. This replaces task 083's explicit player-only gate.
- **2d combat:** ATTACK_PRE, ATTACK_POST, ATTACK_DECLARED (from `ON_ENEMY_ATTACK`), HERO_DAMAGED.

### Phase 3: retire the legacy enum (A-core P3; byte-identical, snapshot regenerated)

- **Trap data, absolute for now:** `TrapCardData.trigger` becomes `trigger_kind` plus an absolute `trigger_side`, so phase 3 keeps today's semantics (the TriggerHandlerTests.gd:3451-3467 probe still passes). Phase 5 makes it owner-relative.
- **Rune data, owner-relative:** `aura_trigger` / `aura_extra_trigger` / `aura_secondary_trigger` become (kind, whose) with whose = SELF / OPPONENT / ANY relative to the rune's owner. `_apply_rune_aura` resolves whose against the owner instead of calling `mirror_trigger`, and `_is_minion_summoned_trigger` (:845) and the backfill side choice (:824-826) read the kind and whose.
- **TRAP_ROUTES** becomes data rows `[kind, event_side, trap_owner, priority]`; keep every priority (player routes 10/20/30, enemy routes 35).
- **Registry entries** move from absolute events to (kind, whose), bound to an owner when applied: the three loops at CombatSetup.gd:613-616 pass "player", "player" and "enemy". If task 090 has landed, `apply_passive` already takes a side; otherwise add the argument here. `unapply_passive` (CombatSetup.gd:647-652, used by PhaseTransition.gd:106) unregisters the same way.
- Delete `Enums.mirror_trigger`, the legacy `TriggerEvent` values, the shim tables and `EventContext.event_type`.
- `dump_order` prints one line per (kind, side filter), e.g. `TURN_START@player: …`. Regenerate handler_order.txt in a reviewed commit: the diff is renames only, with the same priorities and the same order per (kind, side). Merging a player/enemy pair into one any-side registration is allowed only where the regenerated snapshot shows the same per-side order (the 11 paired handlers; `on_player_turn_environment` / `on_enemy_turn_environment` can become one handler).
- ARCHITECTURE.md: rewrite the "Trigger event system" section (:151-153) and the TrapCardData convention note that task 088 added.

### Phase 4: attack parity (A-paths A3a; behaviour change, latent)

- `_fire_enemy_attack_declared` becomes `_fire_attack_declared(side, attacker, defender)` for both sides, called from `_cmd_attack` (:2775) and `_cmd_attack_hero` (:2799). It fires (ATTACK_DECLARED, side) with `ctx.defender` set (the target minion, or `"player_hero"` / `"enemy_hero"`), keeps the `attack_cancelled` check for both sides, and checks `_friendly_board(side).has(attacker)` instead of `enemy_board`.
- CombatManager fires (ATTACK_PRE, side) and (ATTACK_POST, side) for every attacker: drop the `attacker.owner == "player"` gates at :85, :110, :163, :177. The Korrath talent listeners stay player-filtered until task 090.
- Keep task 057's exit after PRE for both sides: if the defender or the attacker left the board during PRE, the attack is spent (attack_count / EXHAUSTED kept; no strike, POST, pierce or counter; the Critical Strike stack is not spent). `_cmd_attack`'s own `target_gone` check (CombatState.gd:2778-2779) covers only the declaration, not PRE.
- `on_attack_fire_riders` registers once on (ATTACK_POST, any) at priority 30; its declaration registration goes. Enemy riders then fire after damage with a defender, as the player's do.
- The champion listeners stay on (ATTACK_DECLARED, enemy).
- Fix the comments that describe the old split: CombatManager.gd:78-84 ("Player-side only…"), CombatHandlers.gd:443-445, MinionInstance.gd:81.

### Phase 5: trap parity (A-paths A3b; behaviour change, latent)

- Trap triggers become owner-relative like runes: (kind, whose). The four cards become (ATTACK_DECLARED, OPPONENT) for `hidden_ambush` / `smoke_veil`, (SPELL_CAST, OPPONENT) for `silence_trap`, (MINION_SUMMONED, OPPONENT) for `death_trap`.
- Routes for both owners on the same footing: add enemy-owned routes for the player's attack declaration, an enemy minion's death and enemy hero damage, mirroring the player's routes. Mirror the friendly-death rule: an enemy-owned friendly-death trap springs only during the player's turn (today's player rule is `if … ON_PLAYER_MINION_DIED and is_player_turn: return`, :1024-1025). New routes take the priority of the player route they mirror; review it in the snapshot diff.
- `_fire_traps_for` matches kind and resolves whose against the trap's owner (with task 084's TrapInstance, the instance's side).
- An enemy-held Smoke Veil can now cancel a player attack through phase 4's declaration check.
- Rewrite `_trap_route_enemy_trap_on_player_turn_start` (TriggerHandlerTests.gd:3451-3467) to the owner-relative meaning.
- Update the TrapCardData doc comments (task 088 documents today's two conventions) to the single convention.
